# aimd2

Карта логики проекта: диаграммы, которые описывают, **как система себя ведёт и
почему**. Не пересказ кода, а правила, статусы, сценарии и политики, написанные
так, чтобы их читал человек.

Документы лежат в репозитории рядом с кодом, ведёт их ИИ-агент, а привязка к
коду позволяет заметить, когда документ разошёлся с тем, что он описывает.

Требуется Node 22 или новее. Работает на Windows, macOS и Linux.

---

## Зачем

В любом проекте есть знание, которого нет в коде: почему у заявки тринадцать
статусов, какие из них терминальны, кто имеет право двигать её дальше, что
происходит при повторной оплате. Это знание живёт в голове, в переписке и в
тикетах, а через полгода не живёт нигде.

Обычная документация от этого не спасает: её пишут один раз и она молча
протухает. Здесь документ привязан якорем к конкретному месту в коде, и когда
это место переписали, документ помечается разошедшимся. Не «когда-нибудь
устареет», а «вот этот документ уже врёт, вот про какой символ».

Писать и править документы должен агент в вашей ИИ-консоли, а не вы вручную.
Инструмент даёт ему повод, материал и проверку.

## Внедрение в новый проект

Пять шагов, после которых агент в вашей консоли начнёт вести документы сам.
Ниже путь для Claude Code, для Codex смотрите раздел про подключение.

### 1. Движок

```bash
npm i -g aimd2
aimd2 --version
```

### 2. Плагин

В любой сессии Claude Code:

```
/plugin marketplace add onokashino/d2-ai-manager
/plugin install aimd2@aimd2
```

Проверка: `/plugin list` покажет `aimd2@aimd2` и его версию.

**Версии движка и плагина должны совпадать.** Плагин зовёт движок по имени, и
старый движок просто не знает новых команд. Ломаться ничего не будет, но и
работать тоже: хуки молчат по устройству, и вы не поймёте, почему ничего не
происходит. Если плагин обновился, обновите и пакет:

```bash
npm i -g aimd2
claude plugin marketplace update aimd2
```

Плагин приносит сразу всё, настраивать отдельно ничего не нужно:

| Что он даёт | Когда срабатывает |
|---|---|
| правила ведения документов для агента | всегда, это скилл |
| список документов, разошедшихся с кодом | в начале сессии |
| название документа, опирающегося на файл | сразу после правки файла |
| черновик документа дешёвой моделью | в конце каждого ответа агента |

### 3. Карта кода

```bash
cd ~/projects/my-app
aimd2 scan
```

Скан кладёт свою базу в `.aimd2/graph.sqlite`. Добавьте каталог в `.gitignore`:
он локальный, пересобирается сканом и в репозитории не нужен.

```
.aimd2/
```

### 4. Первый документ

```bash
aimd2 logic new "Статусы заявки"
```

Рядом появится `docs/logic/_palette.d2`, общий словарь форм и цветов. Без него
документ не соберётся, потому что шаблон его подключает. Палитру правят под
проект, и повторно она не перезаписывается. **Эти файлы коммитятся**: карта
логики живёт в репозитории и проходит код-ревью вместе с кодом.

### 5. Настройка под репозиторий

```bash
aimd2 serve
```

Откройте `http://localhost:41700/setup`. Там список каталогов проекта с числом
файлов и галочками: отметьте те, что попадают в карту.

**Для монорепозитория это обязательный шаг.** Ничего не отмечено означает весь
репозиторий, и тогда граф вызовов тонет в чужих связях, а подсказки про пробелы
указывают на фронтенд, когда логика живёт в бэкенде. На настоящем монорепо из
898 файлов выбор двух веток сузил карту до 507.

Настройки ложатся в `aimd2.json` в корне репозитория. Файл **коммитится**: он
общий для команды, иначе у каждого будет своя карта и расхождения документов
начнут зависеть от того, чья машина их считала.

```json
{
  "roots": ["apps/backend", "packages"],
  "exclude": ["**/__generated__/**"],
  "docsDir": "docs/logic",
  "model": "haiku",
  "studio": { "autoStart": true, "idleMinutes": 60 }
}
```

Каждое поле необязательно, пропущенное берётся по умолчанию. После правки нужен
новый `aimd2 scan`: на уже построенную карту настройки задним числом не влияют.

### 6. Проверка, что всё сцепилось

```bash
aimd2 logic check
```

Дальше просто работайте как обычно. Первый же раз, когда агент тронет файл, на
который опирается документ, он об этом узнает.

Посмотреть на результат глазами: `aimd2 serve` откроет студию на
`http://localhost:41700`, там библиотека документов, редактор с живым
предпросмотром и справочник по синтаксису D2.

### Что положить в репозиторий, а что нет

| Путь | В репозиторий |
|---|---|
| `docs/logic/*.d2` | да, это и есть карта логики |
| `aimd2.json` | да, настройки общие для команды |
| `.aimd2/` | нет, локальная база |
| `.claude/settings.json` | не нужен, хуки приходят от плагина |
| `.codex/hooks.json` | да, если в команде пользуются Codex |

## Другие способы установки

Обычный путь это `npm i -g aimd2` из раздела выше. Ниже то, что пригодится,
если хочется работать с исходниками или без глобальной установки.

### Из исходников

```bash
git clone https://github.com/onokashino/d2-ai-manager.git aimd2
cd aimd2
npm install
npm run build
npm link
```

`npm link` делает команду `aimd2` доступной из любого каталога, как и
глобальная установка.

### Без глобальной установки

Если связывать глобально не хочется, зовите сборку напрямую:

```bash
node /путь/к/aimd2/dist/cli/index.js scan --path ~/projects/my-app
```

Для хуков в этом случае пригодится флаг `--local`, см. ниже.

### Проверка

```bash
aimd2 --help
aimd2 scan --estimate      # сколько файлов попадёт в карту, база не создаётся
```

## Подключение к ИИ-консоли

Сам по себе инструмент только считает и показывает. Работать документы
начинают тогда, когда о них узнаёт агент. Для этого нужны две вещи: **хук**,
который приносит агенту сигнал, и **скилл**, который объясняет, что с этим
сигналом делать.

### Claude Code

Всё приносит плагин, см. шаг 2 внедрения выше. Движок при этом нужен всё
равно: плагин зовёт `aimd2`, поставленный из npm. Пока его нет, хук молчит и
работе не мешает.

### Codex и установка вручную

Плагинов у Codex нет, там хук прописывается командой. Она же пригодится, если
вы не хотите ставить плагин в Claude Code:

```bash
cd ~/projects/my-app
aimd2 init                # обе консоли сразу
aimd2 init claude         # только Claude Code
aimd2 init codex          # только Codex
aimd2 init --local        # хук зовёт сборку по абсолютному пути, без npm link
```

| Консоль | Куда пишется |
|---|---|
| Claude Code | `.claude/settings.json` |
| Codex | `.codex/hooks.json` |

Настройки **дописываются, а не переписываются**: в этих файлах лежат права,
переменные и чужие хуки, и терять их нельзя. Повторный запуск ничего не
испортит.

Что это даёт:

- **в начале сессии** агент получает список документов, разошедшихся с кодом;
- **после правки файла** агент узнаёт, что на этот файл опирается документ.

Второе не значит, что документ обязательно надо править. Это повод подумать,
изменилось ли описанное поведение.

Хук молчит, если документов нет, если файл ничем не связан и если на вход
пришло что-то незнакомое: сломанный хук не должен мешать работе. Проверка
после правки не ходит в базу и не сканирует, она только читает шапки
документов, поэтому отвечает за доли секунды.

### Скилл при установке вручную

В каталоге `skills/logic-documents` лежат правила: когда заводить документ,
когда править, когда не трогать, как выбирать форму под роль, что проверить
перед тем, как закончить. Плагин подключает их сам, а без него скопируйте
каталог в свой проект:

```bash
mkdir -p .claude/skills
cp -r "$(npm root -g)/aimd2/skills/logic-documents" .claude/skills/
```

**Codex:** сошлитесь на файл из `AGENTS.md` в корне проекта, например строкой
«Правила ведения документов логики: `.aimd2/logic-documents.md`», положив копию
рядом.

Без скилла агент увидит сигнал, но не будет знать, какой формы ждут от
документа и почему нельзя ставить статус `approved` своей рукой.

## Как этим пользоваться

Обычный день выглядит так.

**Вы меняете код.** Агент правит `src/order/status.ts`. Хук отвечает: на этот
файл опирается документ «Статусы заявки».

**Агент берёт материал.** Команда `aimd2 logic brief docs/logic/order-status.d2`
кладёт рядом сам документ, состояние каждого якоря и код, который под ним лежит
сейчас. Читать репозиторий руками не нужно.

**Агент правит документ** и отмечает сверку:

```bash
aimd2 logic seal docs/logic/order-status.d2
```

**Вы читаете.** Открываете студию, смотрите диаграмму. Если согласны, нажимаете
«Сверено»: теперь в документе написано, что его читал человек, а не только
агент. Статус `approved` тоже ставите вы, не агент.

**Перед коммитом.** `aimd2 logic check` возвращает ненулевой код, если
что-то разошлось. Годится для pre-commit хука и для CI.

Найти, чего ещё не хватает, помогает `aimd2 logic gaps`: файлы, на которые не
смотрит ни один документ, сверху те, от которых зависит больше всего
остального. Это подсказка, а не список задач.

## Команды

```
aimd2 scan                    построить или обновить карту кода
aimd2 status                  что сейчас в карте
aimd2 serve                   открыть студию, по умолчанию порт 41700
aimd2 logic list              документы логики
aimd2 logic new "Название"    завести документ
aimd2 logic check             сверить документы с кодом
aimd2 logic brief [файл]      документ и код под его якорями разом
aimd2 logic gaps              файлы, на которые не смотрит ни один документ
aimd2 logic trace <файл:символ> настоящий путь вызовов из этой точки
aimd2 logic seal <файл>       отметить, что документ сверен
aimd2 init [claude] [codex]   прописать хуки в настройки ИИ-консоли
aimd2 hook                    точка входа для хуков, читает событие со stdin
```

| Флаг | Что делает |
|---|---|
| `--path <dir>` | корень проекта, по умолчанию текущий каталог |
| `--estimate` | только смета, база не создаётся |
| `--port <n>` | порт студии, по умолчанию 41700 |
| `--local` | хук зовёт эту сборку по абсолютному пути, без npm link |
| `--human` | отметку о сверке ставит человек, а не агент |
| `--depth <n>` | насколько глубоко идёт `trace`, по умолчанию 3 |
| `--model <имя>` | дешёвая модель для черновиков, по умолчанию `haiku` |

## Как устроен документ

Файл `.d2` в `docs/logic`. Обычный [D2](https://d2lang.com), поэтому откроется
любым сторонним инструментом. Первые строки это шапка из комментариев:

```
# title: Статусы заявки
# status: review
# area: Orders
# summary: Тринадцать кодов жизненного цикла, кто их двигает и какие терминальны.
# updated: 2026-09-22
# anchors: src/order/status.ts:OrderStatus@a337be4bbc4ada9d
# checked: human 2026-09-23

...@_palette

created: Создана { class: state }
paid: Оплачена { class: state }
created -> paid: оплата прошла
```

Роль сущности задаётся классом из палитры, а не ручным стилем: так одинаковые
вещи выглядят одинаково во всех документах.

Объяснение вешается на узел полем `tooltip`, а не блоком текста на полотне:
блок участвует в раскладке наравне с шагами, растягивает её и делает схему
нечитаемой. Подсказка на раскладку не влияет совсем, а студия показывает её
при наведении.

## Сверка с кодом

Якорь указывает на файл и, необязательно, на символ. Хвост через собачку это
отпечаток кода, с которым документ сверяли:

```
# anchors: src/order/status.ts:OrderStatus@a337be4bbc4ada9d
```

Отпечаток ловит случай, который иначе проходит незамеченным: файл на месте,
символ на месте, а тело переписали, и документ тихо врёт. Различаются три
состояния:

| что видно | что значит |
|---|---|
| файла нет | код удалён, документ описывает несуществующее |
| символа нет | функция или класс исчезли из оставшегося файла |
| код переписали | тело изменилось после сверки, документ надо перечитать |

Пока отпечатка нет, расхождение не показывается: сверять не с чем, а ложная
тревога хуже молчания.

Отметка записывает, **кто** сверял:

```
# checked: agent 2026-09-23
```

Агент ставит `agent`, человек ставит `human` кнопкой в студии или флагом
`--human`. Это и есть главный ответ на вопрос о доверии: документ, который
агент и написал, и сам объявил верным, иначе выглядел бы так же, как
прочитанный человеком. Библиотека помечает такие отдельно, а `logic check`
называет их и возвращает ненулевой код.

Статус `approved` это слово человека, и оно перестаёт действовать, когда код
под якорем переписали. Такой документ показывается устаревшим, хотя в файле
остаётся то, что человек написал: переписывать чужое заявление за него
инструмент не вправе.

Переформатирование правкой не считается: хеш берётся от текста без разницы в
пробелах, и прогон форматтера документы не тревожит.

## Студия

`aimd2 serve` поднимает локальный сервер, наружу ничего не ходит.

| Адрес | Что там |
|---|---|
| `/` | библиотека документов: статус, область, состояние якорей, поиск |
| `/d/<путь>` | документ: диаграмма, редактор с подсветкой, живой предпросмотр |
| `/setup` | настройка проекта: что попадает в карту, где документы, поведение студии |
| `/guide` | справочник по D2 с живыми примерами и таблицей ролей из палитры |
| `/graph` | карта кода: файлы, символы и связи между ними |

Интерфейс переключается между русским и английским. Сами документы не
переводятся: карта логики это данные проекта, а не текст интерфейса, и второй
вариант разойдётся с первым при первой же правке.

## Ход через код

Якорь отвечает, правда ли ещё каждая точка по отдельности. Но поведение обычно
идёт цепочкой через несколько файлов, и рвётся такая цепочка незаметно: обе
функции на месте, а вызова между ними больше нет. Якоря этого не видят.

Цепочка пишется в шапке отдельной строкой:

```
# flow: src/order/api.ts:createOrder -> src/order/service.ts:place -> src/order/repo.ts:insert
```

Выдумывать её не надо, настоящий путь показывает команда:

```bash
aimd2 logic trace src/order/api.ts:createOrder
```

Проверка следит за ходом двумя разными мерами, и это важно. Пропавший шаг это
факт той же силы, что и сломанный якорь. Пропавший переход это подозрение:
карта вызовов знает вызовы по имени и не знает вызовов через точку, вроде
`service.place()`, поэтому она говорит «проверьте» и не роняет сборку. Иначе
через неделю ложных тревог предупреждения перестанут читать вообще.

## Фоновый писатель

После каждого ответа агента плагин запускает отдельную дешёвую модель. Она
читает ход работы, **включая рассуждения**, а не только итоговый дифф: из диффа
не видно, почему код стал таким, а документ логики отвечает как раз на «почему».

Дальше она либо правит документ, которого коснулась правка, либо заводит новый,
если поведение прошло по нескольким файлам и эти файлы связаны вызовами, то есть
это части одного хода, а не независимые мелочи.

Границы у неё жёсткие, и они не случайны:

| Что | Почему |
|---|---|
| не ставит отметку о сверке | переписать текст и заявить, что он сверен с кодом, это разные действия |
| не трогает документы со статусом `approved` | слово человека фоновая модель переписывать не вправе |
| не переписывает существующее описание, только заполняет пустое | описание видно в списке, и подмена рассказа о поведении записью «добавлено то-то» портит библиотеку заметнее любой ошибки в схеме |
| черновик, который не компилируется, выбрасывается | сломанный документ оставляет в библиотеке пустое место |

Черновик кладётся сразу в `docs/logic` со статусом `draft`, поэтому он попадает
в обычный `git diff` и читается там же, где вы и так смотрите изменения.

Модель зовётся через ту же консоль, которой вы пользуетесь, так что отдельный
ключ не нужен. Запуск идёт в стороне и сессию не задерживает.

## Границы

Это MVP, и честнее сказать сразу, чего он не делает.

**Языки.** Символы разбираются для TypeScript, JSX, JavaScript, Python и Rust.
Для остальных якорь можно поставить только на файл целиком: тело функции
отследить не получится.

**Консоли.** Хуки готовы для Claude Code и Codex. Фоновый писатель работает
только в Claude Code: у Codex нет плагинов, и события конца хода тоже нет.

**Вызовы.** Карта знает вызовы по имени, `place()` и `new Order()`, и не знает
вызовов через точку, `service.place()`. Определить статически, чем окажется
`service`, в общем случае нельзя, а ребро наугад дороже отсутствующего: по
ложной связи документ объявят разошедшимся там, где ничего не менялось.

**Rust отдельно.** Символы, якоря и отпечатки работают: `struct`, `enum`,
`trait`, методы из `impl` и функции внутри `mod` различаются правильно и не
сталкиваются друг с другом. А вот связей между файлами на Rust нет. Там
видимость задаётся объявлениями `mod` и раскладкой каталогов, а не путём в
импорте, и вызовы идут через `::` и `self.`, то есть мимо того, что карта
умеет разрешать. Внутри одного файла вызовы видны, между файлами нет.

**Ни одна из моделей не заменяет человека.** Текст пишет агент, которого вы
позвали, а между ходами фоновая дешёвая модель правит черновики. Но ни та, ни
другая документ не подтверждает: сверка с кодом и статус `approved` остаются за
человеком, и это не формальность, а единственное, что отличает проверенный
документ от правдоподобного.

**Проверено на малом.** Работа шла на проектах в сотню файлов; отдельно
замерено поведение на двух тысячах файлов и ста документах. Живого опыта на
чужих проектах пока нет.

## Разработка

```bash
npm test                  тесты
npm run typecheck         проверка типов, включая тесты
npm run check:render      все документы компилируются
npm run check:highlight   подсветка редактора ничего не теряет
npm run build             сборка в dist
```

Карта логики самого инструмента лежит в `docs/logic`: он ведёт документы про
себя теми же средствами, что предлагает вам.
